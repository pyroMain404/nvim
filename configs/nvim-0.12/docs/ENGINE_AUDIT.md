# Engine audit findings

Each entry records a finding from the config engine audit, the file and line where it was observed, the evidence that decided it, and its verdict.

- **H1** — `lua/config/health.lua:595` — compilation database loop assigned without `break`, so `compile_flags.txt` won over `compile_commands.json` — fixed
- **H2** — `lua/config/health.lua:141` — `rustup show active-toolchain` returning nil reported as green `active toolchain: unknown` — fixed
- **H3** — `lua/config/health.lua:193` — `node --version` spawned twice in Angular section; now reused from `report()` — fixed
- **L4** — `after/ftplugin/gdscript.lua:81` — `vim.opt_local.isfname:append(':')` mutates the global `isfname` option in Neovim 0.12 (`isfname` is global-only); measured `gf` on `res://scripts/tracker.gd` still opens the resolved buffer after removing the append, because the `BufReadCmd` in `plugin/40_plugins.lua` strips the scheme. — fixed
- **L3** — `after/ftplugin/rust.lua:24`, `after/ftplugin/gdscript.lua:186`, `after/ftplugin/markdown.lua:25`, `plugin/41_git.lua:448` — the `buffer` key on `vim.keymap.set`/`del` is deprecated, and its fallthrough on removal makes a buffer-local map global. **Regression caught in this pass**: an earlier commit in this same audit fixed it as `buf = true`, which is invalid (`buf` expects a buffer number, not a boolean — confirmed: `nvim_buf_set_keymap` raises `E5108: Invalid 'buf': Expected Lua number`, and opening a real `.rs`/`.gd` buffer aborted the rest of the ftplugin on load). Corrected to `buf = 0` everywhere, including `41_git.lua:448`; verified by opening real `.rs`, `.gd` and `.md` buffers headless, all load without error. — fixed
- **L8** — `after/ftplugin/markdown.lua:19,22` — used `vim.cmd('setlocal ...')` for window-local options; replaced with `vim.wo[0][0]` assignments as the documented, reproducible way to set window-local options without going through an Ex command. — fixed
- **L9** — `after/lsp/lua_ls.lua:83-90` — the NOTE documented that LuaLS code lens carry an empty command and that disabling them would remove both the count and the empty command, but the returned `settings.Lua` omitted the key; added `codeLens = { enable = false }` and turned the NOTE into the record of the decision. — fixed
- **L7** — `after/ftplugin/cpp.lua:37-40` — `vim.fs.find()`'s `path` option was the buffer's own file path instead of its directory, so the first probe up the tree was `<file>/CMakeLists.txt` (a directory-shaped `stat` on a file, always missing) and an unnamed buffer searched from `''`. Fixed with `vim.fs.dirname(...)`, matching `java.lua`'s own call. — fixed
- **L6** — `after/ftplugin/java.lua:128` — `vim.fs.find(vim.tbl_keys(builds), ...)` tests names in table-key order, which Lua leaves unspecified, so a checkout with both `pom.xml` and a leftover `build.xml` picked between them by hash order instead of precedence. Fixed with an explicit ordered list `{ 'pom.xml', 'build.xml' }`. — fixed
- **E7 / L5** — `after/ftplugin/gdscript.lua:29-72` was the only implementation of the "run `:make` from the project root" remedy, while `compiler/ngc.lua` (Angular) and Maven/Ant both print project-relative paths and `setup_auto_root()` keeps the cwd at the repository root, not the manifest's directory. Extracted as `require('config.run').make_root(markers)` and called, unchanged, from `gdscript.lua`, then newly from `typescript.lua`, `htmlangular.lua` and `java.lua` (guarded on a build being found). Changes Angular/Maven `:make` chdir behavior — `CHANGELOG.md` "Fork changes" entry added. — fixed
- **L1** — `after/ftplugin/cpp.lua` was the only file of the C/C++ pair, so a `.c` buffer (Neovim's own fallback filetype for a header-less file) got no `:compiler` selection, no fold pair, no project `'path'` and no `:Run`, while `clangd`, `clang-format`, the `c` parser and `check_cpp()` all claim the language. Extracted the shared body into a new `after/ftplugin/c.lua`; `cpp.lua` now `runtime!`s it. Verified `.c` and `.cpp` buffers now report identical `foldmethod`/`:Run` state. User-visible for `.c` files — `CHANGELOG.md` "Fork changes" entry added. — fixed
- **H4** — `lua/config/health.lua` — three programs the config assumes were unchecked: `mise` (shelled out to from `ts_ls.lua`, `jdtls.lua` and `health.lua` itself), `rustfmt` (a rustup component, like `cargo-clippy` which already had a check), `make` (a plain-Makefile C/C++ project runs it via the `gcc` compiler plugin). Added all three `report()` calls. — fixed
- **H5** — `lua/config/health.lua:526` — `clang++`'s advice said "nothing compiles" naming `winget install LLVM.LLVM`, worded as if the config depended on invoking it directly, while it compiles through `cmake --build build` or plain `make`. Reworded to name what it actually is: the compiler a CMake/LLVM-configured project builds with. — fixed
- **E9** — `lua/config/health.lua` — the tree-sitter parser-installed check (`#vim.api.nvim_get_runtime_file('parser/'..lang..'.*', false) == 0` then warn/ok) was written out six times (`check_lua`, `check_rust`, `check_angular`, `check_java`, `check_cpp`, `check_godot`), five of them byte-identical apart from the language list. Collapsed into `check_parsers(langs, advice)`, with Lua's different advice (its parser ships with Neovim) passed explicitly. `report_path`/`source_root` helpers from the plan were not extracted this pass — the duplicated shapes they'd collapse (`:265-269`, `:564-572`, `:666-670` in the original numbering) read differently enough per call site (buffer source resolution differs between Angular/C++/Godot in what they fall back to) that collapsing them risked changing which buffer a check reads from; left for a follow-up with its own verification. — fixed (partial)
- **C1** — `init.lua:76` — `nvim_create_augroup('custom-config', {})` was created without `clear = true`, so a `:source $MYVIMRC` (routine while editing this config) duplicates every autocommand registered through `Config.new_autocmd`, including the `PackChanged` hook that runs `:TSUpdate`. The config's other two groups (`plugin/40_plugins.lua`, `after/ftplugin/gdscript.lua`) already pass it. — fixed
- **C2** — `plugin/20_keymaps.lua:19-20` — `[p`/`]p` replace Vim's built-in indent-adjusted put (`:h ]p`) with an unindented one and nothing said so. Added a one-line comment naming the replaced default. No behavior change. — fixed
- **E8** — `after/lsp/ts_ls.lua:46-63` and `after/lsp/jdtls.lua:86-111` — both language servers independently shelled out to `mise ls <tool> --json`, decoded the output, and degraded silently when `mise` was missing. Extracted into `lua/config/mise.lua` as `installed(tool)`, returning a newest-first `{ version, path }` list with `pcall` degradation and session-level memoization so `vim.lsp.enable()` does not pay the blocking query twice for the same tool. Callers keep their own warning strings and version-picking logic, so observable behavior is unchanged. — fixed
- **Phase 4 / language-declaration.md** — the plan proposed a new `.omp/skills/nvim-language-support/references/language-declaration.md` collecting the axis table, the named contracts (`:make`, `:Run`, `gf`, etc.) and the compiler-plugin `errorformat` strategies. On reading `.omp/skills/nvim-language-support/SKILL.md` in full (615 lines), it already carries exactly this content: the axis table (Fase 3), the contracts table with precedence and implementation site (Fase 3), the layer-overlap table (Fase 5 preamble), and the implementation order (Fase 5) pointing at `:h write-compiler-plugin` for a new compiler plugin. A new file would duplicate it almost entirely, which the repo's own rule forbids ("una regola tenuta in due posti diverge"). Not created — rejected (measurement: content already exists).
- **F1** — `plugin/42_format.lua:69` — `Config.format.changed()`'s guard used `#conform.list_formatters(0) == 0` alone, which names only AVAILABLE conform formatters and never counts the LSP fallback `plugin/40_plugins.lua` configures (`lsp_format = 'fallback'`) — a Java buffer (no CLI formatter declared, jdtls formats) and a Lua buffer without `stylua` warned and did nothing on `<Leader>lf` while `<Leader>lF` formatted them through the server, two entry points of one API disagreeing. Fixed: warn only when both conform AND `vim.lsp.get_clients({ method = 'textDocument/formatting' })` are empty. — fixed
- **F2** — `plugin/42_format.lua:100` — `Config.format.changed()` always reported `Formatted %d changed hunk(s)` regardless of whether `format_range` actually edited anything, discarding its `(err, did_edit)` return. Fixed: `format_range` now returns both, and the caller reports `Formatted %d of %d changed hunk(s)` plus a failed count at ERROR when any range errored. — fixed
- **F3** — `plugin/42_format.lua:43` — `local last = vim.api.nvim_buf_get_lines(0, to - 1, to, false)[1] or ''`: when the buffer moved between reading `data.hunks` and the call, `[1]` is `nil` and the `or ''` silently produced a zero-width range. Fixed: skip the range and notify `WARN` instead. — fixed
- **F4** — `plugin/20_keymaps.lua:336` — the Visual `<Leader>lf` mapping called `require('conform').format()` directly, bypassing both of `42_format.lua`'s guards and raising from `require` at keypress if `'conform.nvim'` was not yet loaded. Added `Config.format.selection()` (same guard, then `conform.format()` with no explicit range so conform reads the Visual marks itself) and rebound the mapping to it. — fixed
- **F5** — `plugin/42_format.lua:57,108` (`"conform.nvim" is not loaded yet`) were `WARN`, corrected to `ERROR` per the "requested action failed outright" rule; `:82` (`No diff reference here: formatted the whole buffer`) had no explicit level (defaulting `INFO`), corrected to `WARN`. `:100`, `43_review.lua:116` and `41_git.lua:220` already matched and were left alone. — fixed
