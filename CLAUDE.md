# CLAUDE.md — Neovim config (Windows)

Guida per sessioni future di Claude Code su questa config.

## Convenzioni sui path

I path assoluti specifici della macchina NON compaiono in questo file né negli altri documenti portabili (slash command, skill): si usano solo le terminologie sostitutive qui sotto. I valori reali per la macchina corrente stanno nella memory di Claude (`path-conventions`), che non viaggia col repo. Non dare mai per scontata la struttura delle directory: rileva i path a runtime.

- **`<config-dir>`** — la cartella di questa config (il repo). **Sempre presente**: è la dir su cui gira Neovim (symlinkata dalla dir config standard). A runtime: `git rev-parse --show-toplevel`.
- **`<superproject>`** — il repo contenitore che include la config come **submodule `nvim`**. **Può non esistere**: non darne per scontata la presenza. Rilevalo strutturalmente con `git rev-parse --show-superproject-working-tree` (output vuoto ⇒ assente).
- **`<test-dir>`** — cartella dei file di prova per i test headless.

## Layout del repo

- Questa config vive sul branch **`windows`** di `pyroMain404/nvim`. Il branch `master` remoto contiene una config **diversa e indipendente** (WSL2: lua/core + lua/plugins, snacks, blink-cmp): non mergiare mai i due branch.
  - **Isolamento worktree**: il default branch del repo è `master`, quindi un worktree "fresh" (es. `EnterWorktree` senza specificare la base) parte da `master` = la config sbagliata e disgiunta. Per lavorare isolati su `windows`, crea il worktree a mano dalla base giusta: `git worktree add .claude/worktrees/<nome> -b <branch> origin/windows`. Verifica sempre con `git merge-base --is-ancestor origin/windows HEAD` (deve passare) e la presenza di `lua/user/launch.lua` (marker di windows; `lua/core/` sarebbe master). Le PR hanno base **windows**, mai master.
- Remote `upstream` = `LunarVim/Launch.nvim` (la base originale). È fermo a dicembre 2024 ed è già stato mergiato: non c'è più niente da prendere.
- Il **`<superproject>`** contiene questa config come **submodule `nvim`** (branch windows), quando presente. Dopo ogni push qui, se il `<superproject>` esiste aggiornarlo: dentro il submodule (`<config-dir>`) `git pull --ff-only origin windows`, poi nel `<superproject>` `git add nvim` + commit + push.
- La dir config standard di Neovim (`%LOCALAPPDATA%\nvim` su Windows) è un **symlink** a `<config-dir>`: editare i file qui = editare la config che nvim carica, nessuna copia da sincronizzare né da cercare. Testa headless con `nvim` normale, legge il symlink. La dir dati (`stdpath("data")`, `%LOCALAPPDATA%\nvim-data`) è invece **separata** da `<config-dir>`.
- `lazy-lock.json` è **versionato** (non rimetterlo nel gitignore): garantisce installazioni riproducibili.

## Architettura

- `init.lua` carica i moduli con `spec "user.<nome>"` (helper in `user/launch.lua` che accumula in `LAZY_PLUGIN_SPEC`); un file per plugin in `lua/user/`.
- `lua/user/extras/` NON è caricato: sono opzionali, si attivano aggiungendo `spec "user.extras.<nome>"` in init.lua. Non contarli nei controlli di coerenza.
- Impostazioni per-server LSP in `lua/user/lspsettings/<server>.lua` (caricate con pcall da lspconfig.lua).

## Decisioni prese (non regredire)

- **Neovim 0.12.x**: la config gira su nvim **0.12** (aggiornato da 0.11). `vim.diagnostic.disable/is_disabled` sono stati RIMOSSI; `vim.diff`/`vim.tbl_flatten`/`vim.lsp.get_active_clients`/`buf_get_clients` restano come alias deprecati. La config non usa API rimosse (`:checkhealth vim.deprecated` pulito).
- **treesitter via `tree-sitter-manager.nvim` + core 0.12** (`user/treesitter.lua`): `nvim-treesitter` è stato **archiviato** (apr 2026, sia master sia main congelati). Su 0.12 il motore treesitter è nel core (`vim.treesitter`); `romus204/tree-sitter-manager.nvim` gestisce solo installazione parser (in `stdpath/site/parser`, `.dll` su Windows) e highlight. Il **tree-sitter CLI** arriva da **Mason** (binary github, lista `tools` di `mason.lua`) e compila i parser con **zig** (unico compilatore presente; nessun cc/gcc/clang). NON reintrodurre `nvim-treesitter` né `nvim-treesitter.configs`. I plugin che prima ne dipendevano (markview, neotest, autopairs `check_ts`, ts-context-commentstring, illuminate) usano il core `vim.treesitter`. Perdita nota: l'indent treesitter (`indent={enable=true}`) non è coperto dal core → indent standard per filetype.
- **Commenti via `mini.comment`** (dentro `mini.nvim` branch **stable**, `user/mini.lua`): sostituisce Comment.nvim (fermo dal 2024). nvim ha `gc` nativo dalla 0.10, ma mini.comment mantiene i commenti context-aware via `nvim-ts-context-commentstring` (`options.custom_commentstring`). Keymap `<leader>/` (riga/selezione) + `gc` operatore. NON reintrodurre Comment.nvim.
- **Progetti via modulo nativo** (cartella `user/projects/`): sostituisce project.nvim (abbandonato 2023). La gestione progetti è unificata in `user/projects/`: `init.lua` (auto-chdir alla root con `vim.fs.root`, pattern inc. Cargo.toml/go.mod; history su `stdpath('data')/project_history`; picker telescope `M.pick` — `<c-p>`, `<leader>fp`, bottone alpha) e `group.lua` (gruppi di progetti fratelli, indipendente; usato da telescope `search_dirs` e nvim-tree via `require "user.projects.group"`). Caricato con `require "user.projects"` (NON `spec`: non è un plugin). NON reintrodurre project.nvim.
- **Node deterministica per gli LSP npm** (`user/node/`, `require "user.node"` in init.lua): prepende STATICAMENTE al PATH di nvim la dir della versione fnm fissata (`M.pinned`, oggi **v22.23.1** / npm 10.9.8), così ts_ls/eslint/pyright/cssls/html/jsonls/yamlls/bashls/dockerls/angularls + prettier usano sempre quella Node, indipendentemente da `.node-version`/shell/fnm-non-inizializzato (funziona anche headless). Nessun subprocess (no `fnm env`) → nessun rallentamento. `:checkhealth user.node` SEGNALA con WARNING se manca fnm/versione (degrada al node globale), non silenzia. NON è il provider node (`g:node_host_prog`): quello serve ai remote-plugin, non agli LSP. Python NON è pinnato: pyright usa il venv per-progetto.
- **Provider linguaggio: non disabilitarli** — i warning dei provider mancanti (perl/ruby/node/python3) nel checkhealth vanno lasciati VISIBILI come segnalazione, NON silenziati con `vim.g.loaded_*_provider = 0`. In generale: risolvere solo i warning che sono/possono diventare problemi reali, non azzerarli tutti.
- **LSP**: config per-server via `vim.lsp.config()` in `user/lspconfig.lua`; l'**abilitazione** la fa mason-lspconfig v2 (`automatic_enable`). Non reintrodurre il framework legacy `require("lspconfig")[s].setup` né neodev.
- **which-key v3**: mappature nella chiave `spec` di `setup` o via `wk.add`; MAI `wk.register`, `window`, `ignore_missing` (API v2 rimossa).
- **telescope-fzf-native rimosso**: su Windows la build `make` fallisce e non veniva comunque caricato.
- **Guardia delle dipendenze esterne per i server LSP** (`user/lsp_servers.lua`): l'elenco dei server è centralizzato lì (usato sia da `mason.lua` che da `lspconfig.lua`, invece di duplicarlo) e ogni voce può dichiarare `requires = "<eseguibile>"`. Se l'eseguibile non è nel PATH il server viene escluso da `ensure_installed`/`vim.lsp.config` invece di essere incluso e fallire: senza la guardia, `mason-lspconfig` **ritenta l'installazione fallita ad ogni avvio** (verificato nel sorgente di `ensure_installed.lua`), producendo un errore ogni volta. Torna disponibile da solo al riavvio successivo all'installazione del prerequisito (es. `gopls` richiede `go` nel PATH). Quando si aggiunge un server che dipende da un toolchain esterno (Go, .NET, JDK...), usare questo pattern invece di aggiungerlo direttamente alle liste.
- **Java via nvim-jdtls** (`user/jdtls.lua`), NON via mason-lspconfig: jdtls vuole un client per-progetto con workspace dedicato e un avvio ad-hoc. Perciò jdtls **non** è in `lsp_servers.lua` ed è **escluso da `automatic_enable`** in `mason.lua` (`automatic_enable = { exclude = { "jdtls" } }`), altrimenti girerebbero due client sullo stesso buffer. Avvio manuale con `java -jar` (launcher equinox + `config_win` + `-data <workspace-per-progetto>`, lombok opzionale), così l'unica dipendenza è la JDK, non anche Python. **Guardia di versione, non solo presenza**: eclipse.jdt.ls è compilato per Java 21+, quindi con una JDK più vecchia crasha con `UnsupportedClassVersionError`; `jdtls.lua` risolve la JVM del server preferendo `JAVA_HOME` (gli installer Windows tipo Temurin la impostano su una versione più recente di quella lasciata nel PATH), poi `java` del PATH, e usa la prima JDK >= 21; se nessuna basta non avvia il client e avvisa una volta (pigro, su `ft=java`). Non reintrodurre jdtls in `lsp_servers.lua`/`ensure_installed`. jdtls scrive metadati Eclipse nella root del progetto (`.project`, `.classpath`, `.factorypath`, `.settings/`): sono coperti dal `.gitignore` globale dell'utente (`~/.gitignore_global`, fuori dal repo). La cartella di output `bin/` NON è nel gitignore globale (in altri progetti può essere codice versionato): `jdtls.lua` la ignora solo nei progetti dove gira, aggiungendo `/bin/` al `.git/info/exclude` locale (idempotente).
- **C#/.NET via roslyn.nvim** (`user/roslyn.lua`), NON via mason-lspconfig: come jdtls, `seblyng/roslyn.nvim` risolve da sé il target (soluzione/progetto) e abilita il client, quindi **"roslyn" non è in `lsp_servers.lua`** ed è di fatto FUORI da `automatic_enable` (nessun secondo client in conflitto). Il server (Microsoft.CodeAnalysis.LanguageServer) è un pacchetto Mason del **registry aggiuntivo `github:Crashdummyy/mason-registry`**, aggiunto in `mason.setup{registries=…}` di `mason.lua` **con mason-org elencato esplicitamente** (`registries` SOSTITUISCE il default: ometterlo romperebbe tutti gli altri pacchetti). Si installa dalla lista `tools` di `mason.lua`, **guardato su `dotnet`**: è un processo .NET, senza dotnet nel PATH non parte → spreco scaricarlo (stesso pattern di jdtls/java). Plugin su branch **`main`**, `broad_search=true` + `lock_target=true` (orientato a Unity: la `.sln` è generata accanto ad `Assets/`, non sempre nella cwd, e va fissata dopo il primo attach). `on_attach`/`capabilities` condivisi via `vim.lsp.config("roslyn", …)`. Warning pigro (su `ft=cs`) se manca dotnet. NON reintrodurre roslyn in `lsp_servers.lua`/`ensure_installed`. Prerequisito: **.NET SDK** nel PATH (vedi memory `dotnet-roslyn`).
- **Shader Unity (highlight)** — ftdetect in `user/autocmds.lua`: `.hlsl/.hlsli/.cginc/.compute → hlsl` (parser treesitter `hlsl` **reale**, in `ensure_installed`); `.shader → shaderlab` (il builtin 0.12 lo dà erroneamente a `gdshader`/Godot, `vim.filetype.add` ha priorità). ShaderLab non ha un parser dedicato: `treesitter.lua` registra il parser `hlsl` per il filetype `shaderlab` (`vim.treesitter.language.register("hlsl","shaderlab")`) per highlight **approssimativo** (stesso principio di `.alloy→hcl`; il wrapper ShaderLab non è HLSL, i blocchi CGPROGRAM/HLSL sì). `cs→c_sharp` e `hlsl→hlsl` sono già builtin del core 0.12: non registrarle. commentstring C-style (`// %s`) impostato a mano per hlsl/shaderlab (nel runtime non c'è ftplugin per questi filetype).
- **Debug via nvim-dap** (`user/dap.lua`, `ft=cs`): con nvim-dap-ui (+nvim-nio) e nvim-dap-virtual-text. Unica configurazione: **attach a un editor Unity in esecuzione** con adapter `vstuc` (`type=executable`, `dotnet` sul dll "Visual Studio Tools for Unity.dll" dell'estensione VS Code `visualstudiotoolsforunity.vstuc`); l'endpoint host:porta si scopre con `UnityAttachProbe.dll` dello stesso pacchetto. I dll NON sono ridistribuibili nel repo: risolti a runtime dalle dir estensioni VS Code (stable/insiders/server) o da `vim.g.vstuc_dir`. Se mancano i dll (o manca `dotnet`) l'adapter **non viene registrato** e `<leader>dU` avvisa in modo pigro invece di rompere. La `endPoint` è async: usa il pattern coroutine documentato in `dap.txt` (coroutine sospesa che risveglia la run-coroutine col risultato, o `dap.ABORT`). Keymap sotto `<leader>d` (gruppo which-key già presente). Va esercitato con un editor Unity aperto + estensione vstuc installata.
- **Job in background** (`user/jobs/`): web server, loop di build, avvio app come terminali `toggleterm` **`hidden`** avviati con `Terminal:spawn()` (parte il processo senza finestra, `on_exit` aggiorna lo stato, `close_on_exit = false` così l'output sopravvive). Keymap `<leader>oo` (pannello flottante `user/jobs/panel.lua`) e `<leader>or` (lancio via `vim.ui.select`), agganciati dal config di toggleterm come `floatapps`; stato via `:checkhealth user.jobs`; indicatore `▶ N` in lualine. I task vengono da più sorgenti scoperte con una struttura dichiarativa **detector = precondizione (`when`) → job (`tasks`)**: la lista `DETECTORS` in `user/jobs/providers.lua` (uniti e deduplicati per nome, ordine `local > lua > vscode > npm > maven`). Sorgenti attuali: il nostro `.nvim/tasks.json`, la lista Lua in `user/jobs/config.lua`, la config di altri IDE (`.vscode/tasks.json` in JSONC, script di `package.json` → `<pm> run …`) e i goal Maven quando c'è un `pom.xml` (usa il wrapper `mvnw`/`mvnw.cmd` se presente; aggiunge `spring-boot:run` solo se il pom usa Spring Boot). **Aggiungere il supporto a un tool = aggiungere una riga a `DETECTORS`** (`{ source, when = has_file "…", tasks = fn }`), disattivabile con `cfg.providers[source] = false`; non spargere la logica di scoperta altrove. Il file locale `.nvim/tasks.json` è **JSON dichiarativo** (leggerlo non esegue codice: il comando parte solo al lancio) ed è ignorato aggiungendo `/.nvim/` al `.git/info/exclude` locale (idempotente, stesso pattern del `bin/` di jdtls).
- I tool non-LSP di Mason (stylua e black per none-ls, e **tree-sitter-cli** per la compilazione dei parser treesitter) si auto-installano tramite l'hook mason-registry in `user/mason.lua` (lista `tools`).
- nvim-tree: `filesystem_watchers.ignore_dirs` include `/Temp/rust-analyzer` (rust-analyzer inonda %TEMP% di eventi); l'opzione SOSTITUISCE i default, quindi i default sono ripetuti nella lista.

## Come testare

La procedura headless completa e le trappole verificate (ensure_installed saltato in headless, VeryLazy che non scatta, TSUpdate che mente, exit code sempre 0, MAX_PATH) stanno in `.claude/docs/verifica-headless.md` — **non è una skill** (non compare in `available_skills`, non si auto-attiva): è ciò che legge ed esegue lo Step 1 di `/fine-lavoro`. Per una verifica standalone (senza committare) leggi quel documento e segui i comandi. Non riconvertirlo in skill: la verifica deve restare un passo deliberato. File di prova in `<test-dir>`.

**Delega a Haiku (subagent `nvim-collector`).** `.claude/agents/nvim-collector.md` è un subagent read-only su modello Haiku per la sola fase di **raccolta** — retrieval della doc locale (skill `consulting-nvim-docs`, grep voluminosi) e lancio+cattura dell'output della verifica headless. Confine invalicabile: **raccoglie e riporta grezzo, non interpreta**. Il verdetto (doc → codice; headless pulito/abortisci) resta sempre all'agente principale. Non delegargli `adding-language-support` né gli step di commit/push/bump di `/fine-lavoro`: lì il costo di un errore supera il risparmio di token.
